# AI-radar Web 配置与 R01–R05

## 启动与入口

在项目目录运行 `python3 -m radar serve`，默认地址为 `http://127.0.0.1:8792`。
如果此前的静态服务仍在运行，先结束旧服务，再启动新版本。

- `/setup`：保留三问。第一问只检查 AI 相关性，通过后开放渠道和具体需求；明确非 AI 目标在当前页提示修改。随后按 AI 行业主流含义理解目标并生成渠道关键词，由程序构建计划，使用项目原有 `.env` 中的 `LLM_API_KEY`、`LLM_BASE_URL`、`LLM_MODEL`、`LLM_EXTRA_BODY`、`LLM_TIMEOUT`。
- `/plan`：业务语言预览 R01–R05；确认后新版本生效；拒绝或失败不会替换旧配置。生效后可点击采集。
- `/collect`：采集进度、R04 状态、R05 主题和原始来源、逐阶段 Token/费用、JSON 导出、历史选择、恢复及明确追加预算。
- `/`：没有有效监控配置时跳转 `/setup`；已配置时进入原 dashboard（原静态页面不存在时进入 `/plan`）。

本期不改原 dashboard，新结果仅在 `/collect` 中展示。原 `radar run` 命令仍是旧流程；三个新页面启动的是独立的 R01–R05 流程，不运行旧评分、首页渲染或深挖。

服务为本地单用户用途，默认只监听回环地址；无账号登录或公网部署功能。不要将此配置服务直接暴露到公网。网页不接收、展示或保存 Key。未配置 TikHub Key 时，相应平台不可选。配置生成会产生独立的 Agent 模型费用，但不会自动采集。

## 计划和低成本策略

配置先由 GOAL_AGENT 判断 AI 相关性。随后关键词生成分两阶段：GOAL_PARSE 同时解析目标和 detail，提炼基础词、范围及动态维度 must_cover；CHANNEL_GENERATE 接收完整解析结果和渠道配置，仅生成 channel_keywords。第一阶段 clarification 时停止。第二阶段校验实际搜索词，失败只重试渠道生成。must_cover 不进入前端配置；原始响应与重试记录保存在 wf_draft_steps。详见 [两阶段 Prompt](channel-keywords-prompt.md)。第一问修改后仍须重新校验，后端通过 goal_id 和原始目标精确匹配检查。

渠道词先提炼第一问和第三问，再按渠道生态轻量调整。短目标和长句均由 Agent 提炼，不强制保留原文；程序保留去重后的优先级顺序，核心目标和明确关注词优先于渠道扩展词。X 使用中文表达并保留 FDE 等原有缩写。允许适合多个渠道的短词复用，不强求差异。完整 Prompt 见 [渠道搜索词 Prompt](channel-keywords-prompt.md)。

R03 完全由 `capabilities.build_tasks` 构建。`MENU` 是唯一的采集能力清单，每个参数枚举的第一项是固定默认值。选中渠道就启用其全部能力；支持关键词的能力与该渠道每个实际采用的关键词组合，不支持关键词的能力只执行一个固定参数任务，query 为空。

程序固定每渠道最多 4 个关键词、每任务最多保留 40 条、总任务最多 30 项。先为所有能力生成最小覆盖计划（每项搜索能力使用第一个关键词），再按 `MENU` 渠道顺序轮流增加其余关键词。增加一个关键词时，必须同时覆盖该渠道全部搜索能力。预算不足时截取关键词前缀并在预览说明；如果连最小覆盖计划也超预算，则在配置页报错，不移除能力、不让模型重规划。付费请求预留仍包含最多 3 次尝试，受 `TIKHUB_MAX_CALLS` 和 `TIKHUB_MAX_USD` 控制。

新配置 `schema_version=2`，保留 `goal_interpretation`、实际 `channel_keywords`、原始 `proposed_channel_keywords` 和 `planning_notes` 便于核对。关键词阶段生成的目标解释和整合后的范围仍通过原有 `monitoring_goal`、`monitoring_scope` 字段送入 R04。R04/R05 Prompt、处理逻辑和缓存机制未调整。

有效配置不可变并保留版本，运行时不重新规划。旧配置继续沿用冻结的任务，需重新走配置并确认才采用新规则。新配置预览确认时会复核能力及预算是否变化。

新流程绕过 B站榜单、TikTok、HN 的旧 AI 词库过滤；不调用旧领域专用的分析/评分筛选。程序先按内容 ID 去重、检查文本是否可用、命中历史分析缓存，再按当前配置候选词、来源轮转及新近信息选择候选。每三个关键词命中候选穿插一个未命中候选，保留探索机会。**未命中不判无关，未选中为 pending。** 初始候选最多 160 条，恢复可继续选取剩余候选。

R04 每批至多 20 条，返回相关、不确定、不相关及原因。R05 每批至多 40 条，仅传标题、必要文本和标签；超过一批时，以完全相同的 R05 系统 Prompt 再合并主题，确保跨批聚合。每个返回 ID 必须精确匹配输入，缺失、重复或伪造 ID 拒绝整批入库，保留待处理状态。

R04 批量机制不会刻意逐条发请求；批次末尾或本轮仅剩一条时可自然出现单条批次。R05 单条主题不会被丢弃。不确定内容独立检查，不进入聚合。

## 预算与用量

- R04 + R05 合计目标 ¥0.8，初始上限 ¥1.2；AI 相关性校验与目标理解/关键词生成费用分别展示，与分析费用独立统计（每次目标校验、每次关键词生成分别设 ¥1.2 上限；同一目标的相关性校验可复用）。
- 首次 R04 采用软预算，为 R05 留出余量；R05 在总额度内完成。恢复时可使用硬上限内剩余额度，不重置历史费用。完整处理任意数量的信息不是预算内保证。
- 每次调用前以 UTF-8 字节数保守估算输入上界，加最大输出 Token 预留费用；返回后按 provider 的 `usage` 结算。单价来自 `LLM_PRICE_CNY_PER_M`。
- 失败、超时或缺少 usage 的请求可能已经计费，保留预留额并明确显示；不会记为免费。配置校验纠正调用也计入 Agent 费用。
- 模型响应结构错误不继续无限自动重试；页面可恢复，任何新请求重新执行预算检查。
- Token 数只统计 provider 明确返回的用量；用量未知金额另行显示。费用是按配置单价的估算，不是服务商账单保证。
- TikHub 请求费单独统计；任务按含重试的保守上界占用采集预算。中断或错误任务仍保留其预留，防止恢复绕过上限。采集额度耗尽后仍可分析已采集内容；本期网页追加额度只针对 LLM。

## 历史、缓存和恢复

继续使用原 SQLite 数据库，新增 `wf_*` 表，不引入外部数据库、任务队列或新 Web 框架。

每轮有独立 `runs.id` 和配置版本。原始文本按内容版本去重存储；运行只关联内容版本并保存当轮指标、发布时间和查询信息，不每次完整复制文本。旧目标数据不自动注入新运行。

R04 缓存键包括监控目标、范围、候选词、实际分析文本、Prompt、模型及接口配置。点赞数等指标变化不导致重新分析；语义文本或相关性条件变化时重新判断。R05 输入集合一致可复用；集合变化后重新聚合，不拼接历史主题冒充本轮结果。

后台每次只允许一个任务，连续点击不会并发执行；服务退出后运行可标为中断并恢复。恢复沿用同一 run_id、配置和预算，跳过已成功采集任务与已完成分析批次。R05 批次已完成但跨批合并未完成时，标明为临时批次结果，不视为最终聚合。

采集失败可重试，空结果不反复重试；当前运行没有任何成功结果时也保留错误记录。默认展示当前配置最近一次成功结果，没有成功结果时展示最近一次运行，历史列表保留所有目标。

## 首次付费测试后的修复（分析规则 v2）

- **R04 实质证据**：输入不再把标签当作正文；相关判定必须提供目标对象及实质关系两段原文短引。程序检查短引确实存在于非标签文本，缺失或捏造短引降为 uncertain。证据写入 SQLite 并在逐条结果中显示。语义是否满足目标仍依赖模型判断，离线测试不等于真实准确率保证。
- **R05 统一契约**：普通批次与跨批合并始终使用原始 `item_ids`，不再切换 `member_groups`。合并输入包含原始精简内容，避免只凭上轮摘要继续泛化。
- **保守合并**：多成员主题须提供共同具体对象及逐成员原文短引。缺少依据、仅共享宽泛概念或涉及多个独立 GitHub 仓库时拆回单条，保留全部 ID。类别可宽泛，主题不能只按类别归并。
- **有限纠正与降级**：无效输出最多进行一次预算内纠正，所有调用照常计费。仍失败时展示已完成批次/独立条目并标记未完成，最终跨批失败不再导致页面主题为空。恢复使用成功批次缓存；不自动追加额度。
- **缓存升级**：Prompt 与规则版本变更使旧缓存失效；恢复旧规则运行时重新执行R04判断，但继续使用该run原有预算。旧运行不会自动重跑。
- **时间条件**：新流程X搜索强制附加配置的since日期；GitHub明确使用pushed（默认，最近更新）或created（新建）字段。旧CLI调用不受新流程的强制时间逻辑影响。
- **候选配额**：热搜归属原平台，泛热搜排在正常内容候选之后；所有未入选条目仍保留pending。此处为历史规则说明；当前 R03 已改为程序启用 MENU 中全部固定能力，Agent 不再选择榜单。
- **X诊断**：保留限长且脱敏的上游错误描述，便于区分参数、权限和服务错误。未无依据地将本轮HTTP400归因于某个参数，也未自动切换采集策略。

73项离线测试通过，其中新增真实运行#9样本回归：22条过度合并拆分、标签/虚构引用拦截、候选分配、请求日期参数、跨批字段纠正、失败展示与恢复、旧规则缓存失效。此次修复没有新增付费调用；首次真实测试记录保持原样，尚未进行v2模型实测。

## R04 P0 修复（v3）

R04仍为一个通用Prompt，不按目标更换模板。新增以下输出契约：

- `relation`：direct / adjacent / mention / unrelated / insufficient。
- `evidence_role`：main / promotion / incidental / missing。
- 仅模型判为relevant、关系direct、证据用途main且引用可核对时进入R05。相邻参考、推广或背景提及保留为uncertain，明确无关为irrelevant。个人资料是否直接相关取决于用户目标是否包含人才发现，不一概排除。
- `evidence`和`target_evidence`为带field和quote的原文片段数组。程序存入原始文本、字段及字符起止位置，前端分别展示目标对象和实质依据。
- 引用匹配支持空格、常见排版标点、字母间连字符的差异，以及旧格式省略号拆段；每段仍须独立存在于原文，不能通过近似相似度、翻译或同义词替换放行。数字小数点、负号和否定词不得删除。标签和查询元数据不能充当证据。
- `review_code`区分引用待核对、信息不足、相邻参考、仅提及等原因；原始结果与缓存均保存这些字段。v3 Prompt使旧R04缓存失效，历史结果不会被自动改写或重新收费。

80项离线回归通过。对FDE运行#10因引用不匹配而降级的7条记录进行纯程序重放，有6条引用在新规则下可安全定位，剩余1条仍无法完整匹配，不强行放行。此结果仅证明引用匹配的改进，不代表这6条已重新通过语义判断。记录见 `docs/test-results/fde-p0-offline.json`。

“direct/main”的语义判断仍由模型完成，不能仅凭离线mock测试保证实际精度提升；需后续在固定样本上实测。此次没有新增模型或采集费用，也不调整R05合并策略。

### 微信采集

微信渠道 ID 为 `wechat`，固定能力为 `wechat_article_search` 和 `wechat_video_search`。同一组微信关键词用于两项能力，每个词生成两项任务，沿用每渠道最多 4 词、每任务最多 40 条、总任务最多 30 项和原有预算裁减规则。需配置现有 `TIKHUB_API_KEY`，不增加配置步骤。

公众号调用 `POST /api/v1/wechat_search/v2/fetch_search`（`business_type=article`、`publish_time=week`、`sort=latest`）；视频号调用 `POST /api/v1/wechat_search/v2/fetch_search_videos`（`publish_time=week`、`sort=hot`、`duration=all`）。均使用 `raw=false`，每任务仅取首页、不追加详情请求，单次预估 $0.01，按最多 3 次尝试预留预算。[TikHub 公开接口文档](https://api.tikhub.io/)（2026-10-29 核对）。

结果统一为微信 article/video 条目，去掉搜索高亮，保留接口提供的标题、摘要、作者、链接、时间和指标。文章按稳定链接身份、视频按文档 ID 等去重；跨关键词由现有存储层合并任务来源。接口未给的时间、指标和链接不编造，视频 exportId 保存在 extra；不追加下载、解密或转写。原有 R04/R05 通用分析规则不变。响应格式异常标为错误，部分条目解析失败标为部分完成，不伪装成空结果。
